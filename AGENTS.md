# AGENTS.md

`aared` previews real PPTX, XLSX and DOCX in the browser, with Arabic/RTL
fidelity. **View-only; published on npm as @aared/viewer.** All three
formats have local entries, shared preview, React hooks and `<aared-viewer>`.
`aared-fonts` is frozen/unpublished; browser fonts are the default.

## Rules

1. **Browser text only:** render DOM/SVG, never rasterized text, canvas
   `fillText` or a WASM text shaper. An image-only EMF/WMF decoder would be a
   separate exception, not permission to replace browser text.
2. **Parse in a Worker:** XML/ZIP parsing never runs on the main thread.
   Renderers consume resolved, structured-cloneable models, not XML.
3. **Keep core DOM-free:** it must remain testable headless in plain Bun.
4. **Arabic tables are required:** every touched format must retain a real
   Arabic fixture with a table before its capability is considered complete.
5. **No editing:** no write path, round-tripping or formula recalculation.
6. **Models are read-only:** styles/hyperlinks may be shared; clone before
   modifying. Retained Worker data must be bounded and own its strings/trees.

## Documentation discipline

- **Notes is hard-won engineering experience, not a diary or task journal.**
  Add or extend an entry only for knowledge that would be costly to rediscover:
  native Office semantics, subtle root causes, measured surprises, probe traps,
  or rejected alternatives with evidence explaining why they fail. Routine
  fixes, setup, release administration, progress summaries and test transcripts
  do not warrant an entry. Most tasks should leave Notes unchanged.
- Prefer extending a relevant entry to creating a new one. Keep only the
  evidence and reasoning needed to preserve the lesson; current specifications,
  commands and consumer recipes belong in their owning docs above. Never prune
  unique measurements, probe traps or rejected approaches merely as duplication.
- **The first published release establishes the changelog baseline.** Keep
  CHANGELOG free of entries through that release; do not backfill development
  history or a first-release summary. After it, record user-visible changes
  under Unreleased and group them by version/date when released.
- Research proposals are unchecked until processed point-by-point into their
  canonical homes; do not move them wholesale.

## Environment & commands

Bun required; TypeScript and `tsdown`, including real declaration output.
Implementation lives in `packages/aared/`; site in `site/`, integration/benchmark
UI in `bench/`, optional frozen resolver in `packages/aared-fonts/`.

```sh
bun install
bun run build               # packages; site/bench build separately
bun run typecheck           # packages and tools
bun test                    # headless tests; browser tests skipped
bun run test:visual         # Bun.WebView browser tests + native PPTX/XLSX
bun run test:visual:artifacts
bun run tools --help        # review, bench, inspect, check, doctor
bun run tools review <file> # native + aared captures and review.html
```

**Build first** for Worker/dist tests, consumer checks, bench and site: they
read `dist`, with no source fallback. After rebuilding, restart the bench dev
server and hard-refresh; keep one server on the known port.
Build the site (`bun run docs:build`) and bench (`bun run --cwd bench build`)
before visual tests that serve their production output; those tests verify the
`/aared/` deployment base and measurement entrypoint isolation too.

Office/WebView automation needs a real Windows environment. Sandbox launch
failures are not renderer defects and do not require Bash; use scoped approval
where needed. Details: [Word review](tools/review/docx/README.md).

## Capability delivery

- Before implementation, state the missing capability, normal consumer result,
  affected layers/routes and proof. Deliver one coherent usable capability,
  not a primitive with its obvious usability pieces deferred.
- Evaluate the complete consumer task: imports, host sizing, state, errors,
  cancellation, cleanup and extra opens. A shorter snippet is not a simpler
  API if it hides required work. Put usable recipes in Getting started,
  contracts in the API reference and hard-won tradeoff evidence in Notes.
  Undecided proposals stay separate from OPEN commitments. Code/content review
  is not a measured usability study.
- Assess every affected format and embed route. Mark a route unchanged only
  when shared coverage really handles it; document and test that reuse.
- **Good enough beats perfect:** stop at normal-use correctness; record
  unnoticeable cosmetic residue instead of chasing pixels/rare refinements.
  Visible wrong layout, clipping or wrong-page content is a bug, not polish.
  "CSS can't do it" is not a stopping reason: use browser text or ask before
  accepting the difference. Propose a stopping point when costs outweigh value.
- Avoid unrelated work and needless abstractions, not required capability scope.
  If only a foundation lands, record the missing pieces as OPEN in the inventory.

## Root-cause discipline

1. Trace the source OOXML, resolved Worker model, rendered DOM/SVG, embedding
   styles and native Office evidence before patching a symptom.
2. Inspect shared helpers, defaults and inheritance; check callers and all
   affected routes. Put a rule needed by two formats in its shared home once,
   parameterizing genuine dialect differences.
3. Prefer a focused structural correction over a workaround; preserve contracts
   unless their change is deliberate and documented. Cover related edge cases.
4. Validate the original scenario, host context and shared paths. Re-read real
   output; use paired native review for fidelity and an Office probe for unclear
   OOXML semantics, rather than guessing a CSS approximation.
5. Update current rules/limits/gaps in ARCHITECTURE and keep API/README and
   affected Getting started recipes in step. Use Notes only when the finding
   meets Documentation discipline above; preserve its root cause, evidence and
   relevant scope, not a task recap. Update CHANGELOG only for changes after
   the first published release.
6. Closing a gap means distilling durable facts into their owning docs plus a
   standalone parse-site comment, fixture and test; then delete/shrink the row,
   never turn it into a "done" narrative. Only OPEN rows are commitments.
   Accepted/by-design differences may reopen on meaningful evidence or user
   direction. Give each difference one consistent disposition.

## Implementation guardrails

These are easy-to-break constraints; read the linked design for full mechanics.

- **Packaging:** preserve the literal Worker constructor, flat Worker output,
  `dist/core/` shared chunks and PPTX-only preset catalogue. Keep useful laziness
  on the main thread. Shipped JS must stay Latin-1; use `core/chars.ts` for wider
  characters and ASCII punctuation in messages. Escapes/constant expressions
  may be folded into raw characters. See [build boundaries](docs/ARCHITECTURE.md#build-and-lazy-boundaries).
- **Worker lifecycle:** dead Workers report `worker-error`, not `aborted`.
  Tests swapping `globalThis.Worker` call `drainWorkerPool()` in `finally`.
  Use `ownString`/`ownTree` for retained XML data. Abort helpers come from
  `core/errors.ts`, `FontResolver` from `core/index.ts`.
- **Search:** text-only PPTX/XLSX reads must not load models. Changes to painted
  PPTX words also update `readPptxSlideText` and its fixture parity tests.
- **Painting:** reuse shared fill/gradient/effect helpers, lazy loaders and
  geometry text rectangles; do not silently paint unsupported fills as none.
  Preserve DOCX's untransformed frame / surface / content split and autofit
  behavior. See [paint rules](docs/ARCHITECTURE.md#geometry-fills-pictures-and-effects)
  and [text boxes](docs/ARCHITECTURE.md#text-boxes).
- **Host/layout:** defaults are classes, authored values inline; test defaults
  with `getComputedStyle`. Preserve scroll on content replacement. State inline
  element display explicitly and check in the bench's host CSS, not just tests.
  Await `awaitDocumentFonts(model)` before measuring painted text/fonts.
- **Diagnostics:** `MARK_FALLBACKS` gates development chrome, not fallback
  metadata. Verify built output: no fallback notice or Worker preset catalogue;
  missing/text-only geometry is not an unsupported authored shape.
- **CDP:** WebView's `cdp()` reads only its page even with `sessionId`.
  Use `tools/shared/cdp.ts` for Workers and recalibrate after changing it.

## Testing rule

- Every renderer capability ships a test that **re-reads produced DOM/model
  output**, not just an intermediate. Use real Office-authored fixtures for
  format-shape cases; synthetic inputs are for pure-function/input edge cases.
  New fixture files require sign-off; extend existing coverage through Office.
- **Docs-only:** no typecheck, tests or build. If an API/Start checked example
  changes, run `bun test packages/aared/test/api-snippets.test.ts`.
- `docs-parity` requires every public export/type/enum in the API reference;
  removal also needs manual prose cleanup (the reverse is not checked).
  Runnable API/Start examples use `ts check`/`tsx check`, paste whole with imports
  (`file`, `container`, `el` given); signatures remain unmarked. Playground
  snippets are checked too. Reuse shared page text via `site/src/partials/`.
- Browser tests use `packages/aared/test/harness.ts`: `visual`, `withVisualPage`,
  `serveVisual`, `browserModule`. No private gate/server/build harness. Preserve
  `within` timeouts and custom routes/headers through its options. The runner
  stops supplied servers too unless `keepServer` is explicit; each call gets
  isolated page/server state. See [Quality strategy](docs/ARCHITECTURE.md#quality-strategy).
- Run the visual suite after fonts, split wrapping or borrowed-content lifetime
  changes. Select `*.visual.test.ts` files, never titles. Use Bun.WebView, not
  another Playwright/Puppeteer harness.
- Fidelity needs paired **PowerPoint/Excel/Word** output and human inspection
  of typography, bidi and wrapping. Word native review is an explicit tools
  command; read exact span geometry, not guessed screenshot numbers. Font
  changes need `--absent-fonts` evidence too. LibreOffice is not the PPTX/XLSX
  oracle. Prerequisites and specialist commands live in [Tools](tools/README.md).
- Reuse the existing Office export/capture/review and `_common/office.py`
  helpers; do not build parallel automation. Exports replace their
  `tools/out/<format>/<stem>/` folder; keep derived work elsewhere.

## Ground-truth probe

When OOXML meaning is unclear, interact with real Office: snapshot parts before
and after one targeted change in a nested, ignored repo under
`tools/probe/<topic>/`; diff the XML, ignoring incidental save noise.
Codify the finding in a standalone parse-site comment plus fixture/test, then
delete the completed topic. Keep unfinished/other contributors' probes intact.
Follow the [probe workflow](tools/probe/README.md#workflow) and standard shape;
reuse shared helpers. Scratch Office work stays there, not `%TEMP%`.

## Authoring API design

Serve developers and agents with dedicated stateless functions, plain resolved
data, one canonical shape per concept, explicit units/defaults (Office inches),
and actionable structured errors. Prefer async object-form render, one teardown
story and one error model over multiple overloads or lifecycle graphs.

## Published releases

Breaking changes require migration notes; in `0.x` they require a minor bump.
Each release is one commit and a matching annotated version tag after successful
publish. Published versions are immutable; fix/deprecate rather than unpublish.
Only the maintainer publishes with 2FA; agents never receive npm tokens.
`1.0.0` requires frozen API/model decisions and closed release gates.
There is no standalone push/PR CI: run applicable checks locally before pushing.
Pages deployments validate source/version/ancestry against published stable
annotated releases on `main`. Documentation updates keep shipped package and
build inputs unchanged; changes to those inputs require a new published release.
Deployment never rewrites published tags.

## Commits

- **Only commit/amend when explicitly approved.** Inspect status before staging;
  include only intended work, never another contributor's changes.
- A request to commit means **one commit for all work achieved**, code/tests/docs
  together; do not split by files or pieces unless asked.
- Commit messages, code comments, test names and user-visible errors describe
  capabilities/limitations, never milestone or step labels. Task sequencing and
  progress belong in planning, not Notes or permanent capability documentation.
